# Review Drafts (Approval Manager — Phase 7)

The human-in-the-loop gate. Nothing generated by earlier phases reaches
Buffer without passing through this skill. Presents each `status: in_review`
draft and applies exactly one of the seven actions from REQUIREMENTS.md §12.

## Arguments

- **draft-id** (optional) — review one specific draft. If omitted, go
  through every `status: in_review` draft one at a time.

## Process (per draft)

### 1. Present
Show: the full post text, hashtags, character count, viral_score and its
factor breakdown (from the draft's `## Critic Notes` section), linked
visual brief if any, and the assigned `target_date` from its idea. Then
ask which action to take, using these exact seven options (present via
AskUserQuestion when interactive):

- **Approve** — `status: in_review → approved`. Append
  `{action: approved, date, note}` to history. No other field changes.
- **Edit** — ask the user for replacement text (plain chat reply, not a
  multiple-choice question — edits can be arbitrary length). Replace the
  `## Post Text` section with what they provide verbatim. Append
  `{action: edited, date, note: "user-edited"}`. Status stays `in_review`
  so the edited version gets a chance to be re-approved explicitly, not
  auto-approved by editing it.
- **Regenerate** — re-run the `/write-draft` process for this draft's
  idea, replacing the post text entirely. Append
  `{action: regenerated, date}`. Status stays `in_review`.
- **Change Hook** — rewrite only the opening hook line(s), keep the rest
  of the body. Append `{action: hook_changed, date}`. Status stays
  `in_review`.
- **Change Image** — re-run `/generate-visual` for this draft to produce a
  new brief, replacing the old `visual_ids` entry. Append
  `{action: image_changed, date}`.
- **Change Time** — ask for a preferred HH:MM, set the draft's
  `preferred_time`. Append `{action: time_changed, date, note}`.
- **Reject** — `status: in_review → rejected`. Ask for a one-line reason,
  store it in the history note. A rejected draft is never revisited
  automatically.

### 2. Loop
If multiple drafts are pending, move to the next one after each decision.
Only `Approve` and `Reject` end a draft's review; every other action keeps
it `in_review` for another look (possibly in the same session, possibly
later).

## Report back

After each action, confirm what changed. At the end of a run, summarize:
how many approved, rejected, still in_review, and — critically — check the
result against the rolling schedule requirement (REQUIREMENTS.md §10): if
fewer than 2 days' worth of `approved` drafts exist ahead of today, say so
explicitly. (Sending a notification for this is the Scheduler's job in a
later phase, once it actually maintains the queue — this skill just
surfaces the number honestly.)

## Hard rules

- This is the only skill allowed to set `status: approved`.
- Never auto-approve after Edit/Regenerate/Change Hook/Change Image/Change
  Time — those actions produce a revised draft that still needs an
  explicit Approve.
- Never schedule, publish, or call Buffer from here.
- Never silently drop a Reject reason — it's useful signal for future
  idea generation (a future phase could feed rejections back into
  dedup/fatigue detection).
